### 🟡 LOW — 5 issues

#### LOW-1: `install-prompt.tsx` timer type mismatch (`setTimeout` stored as `setInterval`)

**Location:** `src/components/notifications/install-prompt.tsx:58`, `:72`, `:100`

```tsx
const timerRef = useRef<ReturnType<typeof setInterval> | null>(null);
// iOS branch:
timerRef.current = setTimeout(() => setView("ios"), 3_000) as unknown as ReturnType<
  typeof setInterval
>;
// Android branch:
timerRef.current = setInterval(() => { ... }, 1_500);
// Cleanup:
if (timerRef.current !== null) {
  clearInterval(timerRef.current);  // works for timeout IDs by accident
}
```

**Problem:** The ref is typed for `setInterval` but a `setTimeout` is assigned on the iOS path. `clearInterval` happens to clear timeout IDs in most JS runtimes, but this is a semantic/type bug.

**Fix:** Use `ReturnType<typeof setTimeout>` (both `setTimeout` and `setInterval` return `number` in browser DOM, but Node uses different types; `number` is the portable choice).

```tsx
const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
// iOS:
timerRef.current = setTimeout(() => setView("ios"), 3_000);
// Android:
timerRef.current = setInterval(() => { ... }, 1_500) as unknown as ReturnType<typeof setTimeout>;
// Cleanup:
if (timerRef.current !== null) clearTimeout(timerRef.current);
```

#### LOW-2: `push-server.ts` — unbounded concurrency on push sends

**Location:** `src/lib/notifications/push-server.ts:137-164`

```ts
await Promise.all(
  subscriptions.map(async (sub) => { ... })
);
```

**Problem:** If a single user has many devices (e.g., phone + tablet + desktop + re-subscriptions after SW updates), or if a broadcast goes to many users simultaneously, this fires all push requests in parallel. Push services (FCM, APNS, etc.) have rate limits. Unbounded concurrency can cause 429s or connection exhaustion.

**Mitigation:** In practice, a player won't have more than ~3 active subscriptions. This is LOW severity, but consider a concurrency limit (e.g., `p-limit(5)`) if broadcast volumes grow.

#### LOW-3: `extract.ts` — `sliceFunctionBody` uses naive brace counting

**Location:** `digital-twin/scripts/extract.ts:1156-1169`

```ts
function sliceFunctionBody(content: string, startIdx: number): string {
  const open = content.indexOf("{", startIdx);
  let depth = 0;
  for (let i = open; i < content.length; i++) {
    if (content[i] === "{") depth++;
    else if (content[i] === "}") { depth--; if (depth === 0) return ... }
  }
}
```

**Problem:** Brace characters inside template literals, strings, or regexes will throw off the count. If a server action contains a SQL string or a JSON template with braces, extraction of that function's body (and therefore its tables/rpcs/broadcasts/pushes) will be incorrect.

**Impact:** Wrong data in the Action Signature Reference page (missing or extra tables/RPCs/broadcasts).

**Fix:** Add a simple lexer state for `'"` `` ` `` `//` `/*` to skip braces inside literals/comments. Acceptable to defer since this is dev-tooling, not production code.

#### LOW-4: `sw.js` — `client.navigate()` may throw in `notificationclick`

**Location:** `public/sw.js:275-287`

```ts
client.focus();
client.navigate(targetUrl);  // can throw
```

**Problem:** `navigate()` throws if the client is in a state that doesn't permit navigation (e.g., cross-origin iframe, certain security contexts). The promise chain in `event.waitUntil` would reject, potentially surfacing an unhandled rejection in the service worker.

**Fix:** Wrap in try/catch or chain `.catch(() => clients.openWindow(targetUrl))`.

```ts
client.focus();
client.navigate(targetUrl).catch(() => clients.openWindow(targetUrl));
```

#### LOW-5: Emergency cleanup — `setRawMode` throws in non-TTY

**Location:** `tests/helpers/emergency-cleanup.ts:201-206`

```ts
process.stdin.setRawMode(true);  // throws if stdin is not a TTY
```

**Problem:** Running this helper via a CI pipeline, pipe, or IDE terminal that isn't a TTY will crash with `TypeError: process.stdin.setRawMode is not a function`.

**Fix:** Guard with `process.stdin.isTTY` check, or wrap in try/catch and fall back to a plain `readline` prompt.

### 🔵 INFO — 3 notes

#### INFO-1: `push-server.ts` — persistent auth errors don't prune subscriptions

**Location:** `src/lib/notifications/push-server.ts:149-161`

Only HTTP 410 (Gone) and 404 prune the subscription. A 401/403 (VAPID auth mismatch) or 500 (server error) will retry on the next notification. For persistent 401s (e.g., VAPID keys rotated), the endpoint will be retried forever. Consider pruning on a small number of consecutive non-transient failures, or track a `failures` counter column.

---

#### INFO-2: `state-machines.astro` — Mermaid diagrams require client-side JS

**Location:** `digital-twin/src/pages/state-machines.astro:92`

```astro
<pre class="mermaid">{sm.diagramSource}</pre>
```

The Mermaid diagrams are rendered client-side. If the Mermaid script fails to load (network, ad-blocker, CSP), the page shows raw text diagrams instead of rendered graphs. For a dev tool this is acceptable, but consider server-side rendering via `mermaid.render()` at build time for zero-dependency pages.

---

#### INFO-3: `extract.ts` — drift detection doesn't compare column types

**Location:** `digital-twin/scripts/extract.ts:998-1056`

`computeDrift` checks for column name presence/absence but not whether the TypeScript type matches the live DB column type (e.g., `text` vs `varchar`, `integer` vs `bigint`). Adding type comparison would catch migrations that rename a column but accidentally change its type.
