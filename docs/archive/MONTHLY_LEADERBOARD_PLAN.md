## 1. Data Layer & Database Strategy (Supabase)

### 1.1 New RPC — `get_monthly_leaderboard`

A single parameterized function, aggregating **one month's slice** of completed matches. Mirrors the exact win/points math of `v_session_leaderboard`, but:
- filtered to a **Manila-month range**, and
- reads the **base tables** (`match_players` ⋈ `matches`), **not** `v_match_history` — the view computes per-row `teammates`/`opponents` arrays the leaderboard discards. The all-time matview pays that cost once; a live query must not pay it every call.

```sql
-- p_year / p_month identify the Manila calendar month.
CREATE OR REPLACE FUNCTION public.get_monthly_leaderboard(p_year int, p_month int)
RETURNS TABLE (
  player_id uuid, display_name text,
  games_played int, wins int, losses int,
  points_for int, points_against int, point_diff int, win_pct numeric
)
LANGUAGE sql STABLE SECURITY INVOKER          -- O-3
AS $$
  WITH bounds AS (
    -- Compute the month's [start, end) as UTC instants from Manila wall-clock ONCE,
    -- so the row filter is a plain range scan on completed_at (index-friendly) rather
    -- than a per-row `completed_at AT TIME ZONE ...` (which can't use a btree index).
    SELECT
      make_timestamptz(p_year, p_month, 1, 0, 0, 0, 'Asia/Manila')                        AS m_start,
      make_timestamptz(p_year, p_month, 1, 0, 0, 0, 'Asia/Manila') + interval '1 month'   AS m_end
  ),
  match_results AS (
    SELECT
      mp.player_id,
      CASE WHEN (mp.team='a' AND m.team_a_score > m.team_b_score)
             OR (mp.team='b' AND m.team_b_score > m.team_a_score) THEN 1 ELSE 0 END AS won,
      CASE WHEN mp.team='a' THEN COALESCE(m.team_a_score,0) ELSE COALESCE(m.team_b_score,0) END AS pts_for,
      CASE WHEN mp.team='a' THEN COALESCE(m.team_b_score,0) ELSE COALESCE(m.team_a_score,0) END AS pts_against
    FROM matches m
    JOIN match_players mp ON mp.match_id = m.id
    CROSS JOIN bounds b
    WHERE m.status = 'completed'
      AND m.completed_at >= b.m_start
      AND m.completed_at <  b.m_end
  )
  SELECT
    mr.player_id, p.display_name,
    COUNT(*)::int, SUM(mr.won)::int, (COUNT(*)-SUM(mr.won))::int,
    SUM(mr.pts_for)::int, SUM(mr.pts_against)::int,
    (SUM(mr.pts_for)-SUM(mr.pts_against))::int,
    ROUND(SUM(mr.won)::numeric / NULLIF(COUNT(*),0) * 100, 1)
  FROM match_results mr
  JOIN public.profiles p ON p.id = mr.player_id
  GROUP BY mr.player_id, p.display_name;
$$;

GRANT EXECUTE ON FUNCTION public.get_monthly_leaderboard(int,int) TO anon, authenticated;
```

Returns the same column set as `v_session_leaderboard` minus `session_id`. The `MIN_GP=8` gate and confidence sort are applied in the **action layer** (same as today), so the RPC stays a pure aggregator.

### 1.2 New RPC — `get_leaderboard_months` (picker source, D7)

```sql
CREATE OR REPLACE FUNCTION public.get_leaderboard_months()
RETURNS TABLE (year int, month int)
LANGUAGE sql STABLE SECURITY INVOKER
AS $$
  -- Distinct Manila-months that actually have completed matches, plus the current
  -- Manila month (so the current month is always selectable even when empty — D7),
  -- newest first.
  SELECT DISTINCT
    EXTRACT(YEAR  FROM (completed_at AT TIME ZONE 'Asia/Manila'))::int,
    EXTRACT(MONTH FROM (completed_at AT TIME ZONE 'Asia/Manila'))::int
  FROM matches WHERE status='completed' AND completed_at IS NOT NULL
  UNION
  SELECT EXTRACT(YEAR FROM now() AT TIME ZONE 'Asia/Manila')::int,
         EXTRACT(MONTH FROM now() AT TIME ZONE 'Asia/Manila')::int
  ORDER BY 1 DESC, 2 DESC;
$$;
GRANT EXECUTE ON FUNCTION public.get_leaderboard_months() TO anon, authenticated;
```

This is the only place a per-row `AT TIME ZONE` runs, and it's a cheap distinct over the partial index — acceptable for a picker that's fetched once.

### 1.3 Performance (concern: matches table grows)

- **New partial index** so each monthly query is a bounded range scan regardless of total table size:
  ```sql
  CREATE INDEX IF NOT EXISTS idx_matches_completed_at
    ON public.matches (completed_at) WHERE status = 'completed';
  ```
- The boundary math (§1.1) keeps the filter as `completed_at >= start AND completed_at < end` — a sargable range that uses the index. A month is tens-to-hundreds of rows; this stays fast for years.
- No materialized view, no refresh plumbing, no staleness — the live query is always current and cheap because it never scans more than one month.

### 1.4 RLS / authorization  *(corrected after live-DB review)*

`matches` **does have RLS enabled** — but the `matches_select` policy is **permissive for reads**: it allows `anon`/`authenticated` to read any row where `status <> 'pending' OR is_published OR <organizer>`. Completed matches always satisfy that, so the existing leaderboards already read them publicly.

The monthly RPC uses **`SECURITY INVOKER`**, which means it runs **as the caller and therefore RESPECTS that RLS policy** — exactly what we want: it can only ever aggregate completed matches the caller is allowed to see. (This differs from `get_player_streaks` / `get_alltime_snapshot_before`, which are `SECURITY DEFINER` to bypass RLS; the monthly board doesn't need that.) `STABLE`, `GRANT EXECUTE` to `anon` + `authenticated`. *(O-3 ✅)*

## 2. Logic & State (Next.js Actions & Hooks)

### 2.1 Server actions (`src/app/actions/leaderboard.ts`)

- **`getMonthlyLeaderboard(year, month)`** — calls `get_monthly_leaderboard`, applies `MIN_MONTH_GP=8`, confidence sort with `MONTH_CONFIDENCE_K=6`, the existing rank-assignment + VIP-tag merge. Returns `LeaderboardRow[]` with `rank_movement: null` and (O-2) `win_streak: 0`.
  - **DRY (refined after review):** session, all-time and monthly share the **gate → confidence-sort → rank → VIP-enrich** core, but they differ on one step — all-time computes `rank_movement` from the 7-days-ago snapshot, session/monthly don't. So the shared helper is `rankAndEnrich(rows, { minGP, k, rankMovementFn? })`: session + monthly pass **no** `rankMovementFn` (→ `rank_movement: null`); all-time passes its snapshot-diff function. This keeps the common 90% shared without forcing one board's movement logic on the others.
- **`getLeaderboardMonths()`** — calls `get_leaderboard_months`, returns `{ year, month, label }[]` (label formatted "June 2026" via the Manila constant).
- **`getPlayerMonthlyStats(playerId, year, month)` — NEW, additive (chosen over a union refactor).** The hero card needs the user's own monthly stats (incl. below-threshold). Rather than change `getPlayerStats`'s `(playerId, sessionId|null)` signature — which would force-edit its call site (`use-leaderboard.ts:227`) **and** its test mock (`tests/unit/use-leaderboard.test.ts:96`) and risk other callers — add a **separate** monthly function. Zero risk to existing callers.

### 2.2 Hook (`src/hooks/use-leaderboard.ts`)

- Widen `scopeTab` to **`"session" | "monthly" | "alltime"`**.
- **Change the initial `scopeTab` default** (currently `use-leaderboard.ts:121` defaults to `"alltime"` when there's no session): make it `initialSessionId ? "session" : "monthly"` so the lobby opens on the current month (O-1).
- Add `activeMonth: { year, month }` initialized to the **current Manila month** (derive from `now()` shifted to `Asia/Manila`, not the browser tz, so it matches the DB's month definition), `availableMonths`, `monthlyRows`, `monthlyLoading`, `fetchMonthlySeq` guard, `handleMonthPick`. The current-month default re-derives on mount so it rolls over naturally — no cron.
- Reuse the existing `fetchSeq` stale-guard, flash-on-new-entrant, and lazy-load-on-first-visit patterns verbatim for the monthly tab. **Switching months** bumps `fetchMonthlySeq` so a slow prior-month fetch can't overwrite the new one.
- **Realtime:** when `scopeTab==='monthly'` **and** viewing the **current** month **and** there's an active session in context, subscribe to `subscribeToMatches` (same 500ms debounce) so the board updates live during play. Past months are static (no subscription).

This keeps one hook owning all three scopes — no parallel hook, architecture stays DRY.

## 4. Edge Cases & Timezones

- **Month boundary (Manila):** computed once as `[make_timestamptz(y,m,1,…,'Asia/Manila'), +1 month)` UTC instants, then a plain range scan on `completed_at`. Manila is **UTC+8 exactly** (no half-hour offset), so midnight Manila = **16:00 UTC the previous day**. **Verified live:** `make_timestamptz(2026,7,1,0,0,0,'Asia/Manila')` = `2026-06-30 16:00:00+00`. Worked example: a match with `completed_at = 2026-06-30 16:01 UTC` is **2026-07-01 00:01 in Manila**, so it sits **on/after** the July boundary (`2026-06-30 16:00 UTC`) and correctly counts in **July** — even though its UTC date is still June 30. Anchoring in Manila is what makes that right.
- **No DST:** `Asia/Manila` is a stable UTC+8 with no daylight saving, so there's no spring-forward/fall-back boundary ambiguity. (If the club's timezone ever changes to a DST zone, revisit the boundary math.)
- **Month rollover:** the default month is derived from `now() AT TIME ZONE 'Asia/Manila'` per request, so it advances to the new month automatically at Manila midnight on the 1st — no scheduled job.
- **Below-threshold players (<8 games):** excluded from the ranked board but still see their own stats via the hero card (same as session/all-time).
- **Confidence weighting with MIN_GP=8:** an 8–0 month reads strong but won't auto-beat a dominant high-volume player; K=6 tunes that balance.
- **Staleness/concurrency:** `fetchMonthlySeq` guards both tab-switches and month-switches; a stale in-flight fetch is discarded (existing pattern).
- **Constant:** introduce `CLUB_TIMEZONE = 'Asia/Manila'` (the app's first canonical tz) used by the actions for labels and any boundary math, mirroring the SQL constant. Single source of truth.
